# 성능·복원력 시험 보고서

시험 일자: 2026-11-07. 도구: `scripts/load_test.py`(표준 라이브러리만 사용), `scripts/backup.sh`, `scripts/restore.sh`.

## 1. 환경과 한계 (먼저 읽어 주세요)
* 대상: `deploy/docker-compose.prod.yml`을 **개발 PC 한 대**에서 구동(백엔드 컨테이너 메모리 상한 1GiB, Postgres 16, Caddy). 클라이언트(부하 생성기)도 같은 PC.
* 이 PC는 CPU 코어가 매우 많아 **AWS 소형 인스턴스의 성능을 대표하지 않습니다.** 아래 수치는 “소프트웨어가 병목 없이 정확성을 유지하는가”를 보는 용도이며, 용량 산정에는 목표 인스턴스에서 같은 스크립트를 다시 실행해야 합니다.
* 부하 생성기와 서버가 같은 호스트이므로 네트워크 지연·LTE 특성은 반영되지 않았습니다.
* 모든 시험에서 장비 수만큼 키를 **실제 관리자 API로 발급**했고(가짜 우회 없음), 결과 검증은 관리자 API(`/events` 총건수)로 했습니다.

## 2. 수신 시험 결과
| 시나리오 | 요청 수 | 처리량 | p50 | p95 | p99 | 최대 | 상태 코드 | DB 저장 건수 |
|---|---|---|---|---|---|---|---|---|
| 50대 × 20건, 동시 10, 재전송 10%, keep-alive | 1,098 | 1,116 req/s | 8.0 ms | 11.7 ms | 19.0 ms | 67.8 ms | 전부 200 | 1,000 / 1,000 ✔ |
| 1,000대 × 5건, 동시 50, 재전송 10%, keep-alive | 5,468 | 1,089 req/s | 40.2 ms | 83.8 ms | 107.1 ms | 167 ms | 전부 200 | 5,000 / 5,000 ✔ |
| 1,000대 × 3건, 동시 50, 재전송 10%, **요청마다 새 TLS 연결**(실제 LTE 기기 패턴에 가까움) | 3,331 | 662 req/s | 70.2 ms | 112.5 ms | 284.6 ms | 317 ms | 전부 200 | 3,000 / 3,000 ✔ |

* **정확성**: 모든 시나리오에서 재전송(중복) 응답 수 = 보낸 중복 수, DB는 고유 이벤트 수와 정확히 일치(정확히 한 번).
* 1,000대 키 발급(관리자 API 2,000회) 약 12초.
* 부하 중 백엔드 메모리 약 405MiB/1GiB, Postgres 약 59MiB.
* 동시 20스레드가 같은 이벤트를 동시에 보내는 경쟁 조건은 통합 테스트(`concurrentIdenticalPostsInsertExactlyOnce`)로도 검증됩니다.

### 해석
* 실제 트래픽은 “장비 수 × 위반 발생 빈도”인데 위반은 드문 이벤트라, 1,000대여도 평균 수신률은 초당 1건에 크게 못 미칠 가능성이 큽니다(**발생 빈도는 가정이며 확정 자료 없음**). 위 처리량은 그보다 수백 배 여유가 있다는 의미지만, 소형 인스턴스에서는 다시 측정해야 합니다.
* 한계 신호: 동시 접속 50에서 p99가 상승했습니다(대기열). 병목이 부하 생성기(단일 파이썬 프로세스)인지 서버인지는 분리해 측정하지 않았습니다.

## 3. 장애 복원력 시험
| 시험 | 결과 |
|---|---|
| DB 컨테이너 중지 후 기기 요청 | **503 + `Retry-After: 30`**, 응답 본문에 비밀 정보 없음. `/actuator/health`도 503 |
| DB 재기동 | 앱 재시작 없이 **약 2초 내** 정상 응답 복귀 |
| 잘못된 키로 DB 장애 중 요청 | 401이 아니라 503(키 판정이 불가능하므로 기기가 재시도하도록) |
| 백업 → 복구(별도 DB) | 장비 2,051·이벤트 9,001·감사 4,107행 일치, 불변성 트리거·스키마 버전 확인 |
| 백업 파일 1바이트 변조 | 체크섬 불일치로 복구 거부(종료 코드 3) |
| 틀린 패스프레이즈 | 복구 실패(종료 코드 1), 임시 DB 자동 정리 |
| 운영 DB 이름으로 복구 시도 | 거부(종료 코드 2) |

* 복구 소요: 1초 미만(664KB 암호화 백업). **데이터가 커지면 선형 이상으로 늘어납니다.** 실제 RTO는 운영 데이터 크기로 재측정해야 합니다.

## 4. 측정하지 않은 것
* 목표 인스턴스(예: t3.small/medium)에서의 용량, 장시간(수 시간) 지속 부하, DB 풀 고갈, 대량 데이터(수백만 행)에서의 조회·CSV 성능.
* 지도 API(`/map/events`)와 관리자 조회의 대용량 응답 시간.
* 네트워크 단절·패킷 손실 상황.
* 이 항목들은 스테이징에서 `make load-test ARGS="--devices 1000 ..."`로 재현할 수 있습니다(스테이징에서만 실행: 테스트 장비가 남고 원시 이벤트는 삭제할 수 없음).

## 5. 재현 방법
```bash
make prod-env && make prod-up                      # deploy/.env.prod 에서 DOMAIN=localhost, HTTPS_PORT=8443, INGEST_PER_IP_PER_MINUTE=1000000 로 조정
HTTPS_PORT=8443 make load-test ARGS="--devices 1000 --events-per-device 5 --concurrency 50 --retry-rate 0.1"
HTTPS_PORT=8443 make load-test ARGS="--devices 1000 --events-per-device 3 --concurrency 50 --no-keepalive"
```
* 부하 생성기가 한 주소에서 나오므로 `INGEST_PER_IP_PER_MINUTE`를 크게 올려야 합니다(기본 600/분이면 429가 납니다). **운영 값은 올리지 마세요.**
