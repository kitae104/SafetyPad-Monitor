# 펌웨어 연동 런북 (장비 업체 전달용)

> 상태: **서버 구현 기준 초안**. `상태: 협의 필요`로 표시한 항목은 장비 업체의 서면 확인 전까지 확정이 아닙니다.
> 서버가 펌웨어의 동작을 가정하지 않으므로, 아래 요구를 펌웨어가 지킬 수 있는지 먼저 회신해 주세요.

## 1. 연결 정보
| 항목 | 값 |
|---|---|
| 방식 | HTTPS `POST` (JSON). **MQTT(TLS)도 선택 가능** — 규격은 `docs/MQTT_INTEGRATION.md` (저장 규칙은 동일, 저장 확인은 `…/acks` 토픽) |
| URL | `https://<운영 도메인>/api/v1/device-events` (IP 고정 금지, 도메인 사용) |
| 인증 | 헤더 `X-API-Key: <기기별 키>` — 키는 기기마다 다름 |
| Content-Type | `application/json` |
| TLS | TLS 1.2 이상, 공인 CA 인증서(Let's Encrypt), SNI 사용. 인증서 갱신 시 기기 수정이 필요 없도록 **루트 CA를 신뢰 저장소에 탑재**하고 서버 인증서 자체를 고정(pinning)하지 않을 것을 권장 |
| 본문 크기 | 최대 8,192 바이트 (초과 시 413) |
| 속도 제한 | 키당 분당 120회(운영 설정으로 조정 가능). 초과 시 429 + `Retry-After` |

## 2. 요청 본문 (이벤트 1건 = 요청 1건)
```json
{
  "event_id": "PAD-0001-EVT-00001",
  "device_id": "PAD-0001",
  "event_type": "MULTI_RIDE",
  "event_time": "2026-11-05T14:30:10+09:00",
  "gpsData": { "latitude": 37.451448, "longitude": 126.651542 },
  "battery_level": 55
}
```
| 필드 | 필수 | 규칙 |
|---|---|---|
| `event_id` | ✔ | 장비 안에서 이벤트마다 **고유하고, 재전송해도 변하지 않는 값**. 1~100자, `A-Z a-z 0-9 . _ : -` |
| `device_id` | ✔ | 발급받은 키가 속한 장비 ID와 **같아야 함**(다르면 403). 1~64자, 위와 같은 문자 |
| `event_type` | | 생략 시 `MULTI_RIDE`. 다른 값은 422 |
| `event_time` | ✔ | 기기가 이벤트를 감지한 시각. ISO-8601 **+ 시간대 오프셋 필수**(`+09:00` 또는 `Z`). 오프셋이 없으면 422. 미래 10분 초과·366일 초과 과거는 422 |
| `gpsData` | | `{latitude, longitude}` 숫자(WGS84 도, 소수 6자리 권장). 위치를 못 얻었으면 `null`, 생략, `""` 중 하나(상태: 협의 필요 → 하나로 통일 권장: `null`). 위도 -90~90, 경도 -180~180 밖이면 422 |
| `battery_level` | | 정수 0~100 또는 `null` |
| 그 외 필드 | ✘ | 정의되지 않은 필드가 있으면 400 |

* 서버가 `received_at`(최초 수신 시각)을 **직접** 기록합니다. 본문에 넣어도 무시되지 않고 400이 됩니다(미정의 필드).
* 위치가 없는 이벤트도 **반드시 전송**하세요. 서버는 표에는 저장하고 지도에서만 제외합니다.
* (0, 0) 좌표를 “위치 없음” 대신 쓰지 마세요.

## 3. 응답과 재전송 규칙
| HTTP | 의미 | 기기 동작(권고) |
|---|---|---|
| 200 `{"success":true,"duplicate":false}` | 저장 완료(DB 커밋 후에만 응답) | 로컬 큐에서 삭제 |
| 200 `{"success":true,"duplicate":true}` | 이미 저장된 이벤트의 재전송 | 성공으로 간주, 삭제 |
| 400 / 422 | 본문 오류 | **재시도해도 해결되지 않음.** 격리 보관하고 로그를 남김 |
| 401 | 키 없음/미등록/폐기/만료 | 이벤트 보관, 낮은 빈도(예: 15분 이상)로 재시도. 운영자에게 키 확인 요청 |
| 403 | 키와 `device_id` 불일치 또는 장비 비활성 | 위와 동일 |
| 413 | 본문 8KB 초과 | 재시도 금지 |
| 429 | 속도 제한 | `Retry-After` 초만큼 대기 후 재시도 |
| 500 / 502 / 503 / 타임아웃 | 서버·망 일시 장애 | **같은 `event_id`로** 지수 백오프 재시도(예: 30초→1분→2분→…→최대 1시간, ±20% 무작위 지터) |

* 서버가 성공을 응답한 것만 지우세요. 응답을 못 받았다면(타임아웃 등) 저장되었는지 알 수 없으므로 **같은 `event_id`로 다시 보내면** 됩니다. 중복은 서버가 한 건으로 처리합니다.
* 오프라인 중 쌓인 이벤트는 순서와 무관하게 전송해도 됩니다. `event_time`은 발생 시각, 서버 수신 시각은 별도로 남습니다.
* 상태: 협의 필요 — 일괄 전송(배열) 규격, 요청 타임아웃, 백오프 값, 큐 용량.

## 4. 시계(RTC)
* 서버는 수신 시각과 `event_time`의 차이(지연)를 계산합니다. 수신이 발생보다 **60초 넘게 빠르면** 화면에 “시계 오차 의심”으로 표시합니다.
* 기기는 가능하면 NTP/네트워크 시간으로 RTC를 보정하고, 보정 정책(주기, 허용 오차)을 알려 주세요. 상태: 협의 필요.

## 5. 키 발급·교체 절차
1. 운영자가 관리자 화면(장비 관리 → 새 키 발급)에서 키를 발급합니다. **키 원문은 그 순간 한 번만** 보입니다.
2. 운영자가 안전한 경로(예: 공장 프로비저닝 파일, 암호화 전송)로 업체에 전달합니다. 메신저·이메일 본문 전달은 피하세요.
3. 교체: 새 키 발급 → 기기에 반영 → 정상 전송 확인 → 이전 키 폐기. 두 키는 폐기 전까지 모두 유효합니다.
4. 키가 노출되었다고 의심되면 즉시 폐기하고 새 키를 발급합니다. 상태: 협의 필요 — 기기에 키를 주입·교체하는 실제 방법(공장/OTA).
* 키는 `spk_`로 시작하는 약 47자 문자열입니다. 기기에는 평문 저장이 불가피하므로, 가능하면 보안 저장소를 사용하세요.

## 6. 호출 예시
```bash
# 키는 예시 자리표시자입니다. 실제 키를 문서·채팅·저장소에 붙여 넣지 마세요.
curl -sS -X POST https://<운영 도메인>/api/v1/device-events \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $DEVICE_KEY" \
  -d '{"event_id":"PAD-0001-EVT-00001","device_id":"PAD-0001","event_time":"2026-11-05T14:30:10+09:00","gpsData":null,"battery_level":55}'
```

## 7. 인수 시험 체크리스트 (업체와 함께 수행)
스테이징 환경에서 아래를 모두 통과해야 현장 설치로 넘어갑니다. 서버 쪽 자동 검증은 `scripts/smoke.sh`, 부하는 `scripts/load_test.py`로 수행했습니다.

- [ ] 정상 이벤트 → 200, 관리자 화면에 KST 시각으로 표시
- [ ] **동일 `event_id` 10회 전송 → 화면에 1건**, 최초 수신 시각 불변
- [ ] 응답을 일부러 끊은 뒤 재전송 → 1건
- [ ] 오프라인 30분 후 쌓인 이벤트 일괄 전송 → 전부 저장, 순서 무관
- [ ] 잘못된 키 → 401, 다른 장비 키 → 403 (이벤트가 저장되지 않음)
- [ ] GPS 없는 이벤트 → 저장되고 목록에는 보이며 지도에는 없음
- [ ] `battery_level` 생략/`null`/0/100
- [ ] 시간대 오프셋 없는 `event_time` → 422 (기기가 오프셋을 반드시 붙이는지)
- [ ] RTC가 틀린 상태의 이벤트 → “시계 오차 의심” 표시
- [ ] 서버를 잠시 내렸다 올림(503/타임아웃) → 복구 후 자동 재전송으로 유실 없음
- [ ] 인증서 갱신 후에도 접속 유지(루트 CA 신뢰)
- [ ] 키 교체(두 키 동시 유효 → 이전 키 폐기) 무중단 확인

## 8. 이번 범위에 포함되지 않는 것
* **주기 GPS 전송·하트비트**: 원 제안서 확정 사항이 아니므로 서버의 `/api/v1/device-locations`는 **구현하지 않았습니다**. 승인되면 별도 규격으로 추가합니다. 그때까지 화면은 “온라인/오프라인”을 표시하지 않고 `최근 수신`만 표시합니다.
* 양방향 제어, SMS 알림. (MQTT는 `docs/MQTT_INTEGRATION.md`로 제공)
